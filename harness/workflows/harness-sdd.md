# Harness + SDD Workflow

## 目标

把用户需求稳定推进为可评审、可实现、可验证、可追踪、可沉淀的工程交付。

## 阶段

### 0. 上下文装载

读取：

- `AGENTS.md`
- `harness/standards/`
- `harness/specs/svanilla/00-sdd-index.md`
- `harness/specs/svanilla/08-agent-working-rules.md`
- `harness/requirements/README.md`
- `harness/knowledge/README.md`
- `harness/ai-experience/README.md`

输出：

- 影响模块。
- 需要追加读取的 SDD、需求和知识文件。
- 构建和测试入口。
- 初始风险。

### 1. 需求分析

输出必须包含：

- 原始需求。
- 事实。
- 假设。
- 目标。
- 包含范围。
- 不包含范围。
- 约束。
- 可测试验收标准。
- 开放问题。
- 是否需要创建或更新需求文件。

### 2. 规格设计

输出必须包含：

- 涉及模块和文件。
- 接口、数据、状态和运行流程变化。
- 日志设计。
- 错误处理。
- 兼容性影响。
- 自测策略。
- 是否需要更新 SDD。
- 是否需要更新分类知识。

### 3. 评审闸门

检查：

- 验收标准是否可执行。
- 是否触碰持久化、插件 ABI/API、下载状态、线程、Qt 生命周期或构建配置。
- 是否符合 `harness/standards/`。
- 是否需要迁移策略。
- 测试是否覆盖主要风险。
- 是否存在必须先问用户的问题。

评审未通过时，不进入实现；除非用户明确要求快速原型。

### 4. 实现

要求：

- 小步修改。
- 遵循现有风格和团队规范。
- 避免无关重构。
- 行为、接口、数据、构建或测试方式变化时同步更新 SDD。
- 新增稳定实现规律时同步更新 `knowledge/`。

### 5. 代码分析

检查：

- 回归风险。
- 边界条件。
- 线程、Qt 对象生命周期、资源释放。
- 错误路径。
- 日志是否足够定位问题。
- 测试缺口。

### 6. 调试验收

输出：

- 执行的命令。
- 结果。
- 失败原因。
- 未验证内容。
- 残余风险。
- 手工验收步骤。

### 7. 经验沉淀

满足任一条件时必须沉淀：

- 发现文档和代码不一致。
- 发现可复用的模块实现规律。
- 发现构建、测试、Qt、插件、下载、存储相关坑点。
- 本次任务出现返工、误判或验证失败。
- 用户明确要求总结 AI 经验。

沉淀位置：

- AI 协作经验：`harness/ai-experience/`
- 模块实现知识：`harness/knowledge/`
- 团队规范：`harness/standards/`
- 版本需求或落地需求：`harness/requirements/`

## 压缩规则

小任务可以把阶段 0 到 3 合并为一段简短分析，但最终仍要说明验证、风险和是否沉淀经验。
